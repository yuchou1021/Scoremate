| 项 | 值 |

---

## 1. 背景与机会

### 痛点

- 自学者拿到喜欢的曲子，原谱难度远超自己水平，手工简化费时且容易改坏。
- 老师为学生备课，需要同一首曲子适配不同难度/不同调性，重复劳动量大。
- 现有工具要么是纯规则（功能死板），要么是纯生成式 AI（出谱但不可编辑、质量不可控）。
- MuseScore 社区有大量"求改编"的帖子，但**没有面向普通用户的一站式 AI 改编助手**。

### 机会

- 插件 + 云端 + 用户自带 Key 的架构：**零服务器成本、免费开源、可自托管**，天然适合开源作品集项目。
- 规则 + LLM 混合：确定性部分可靠，创意部分灵活，且输出可校验、可回滚。

---

## 2. 产品定位

> **一句话**：在 MuseScore 里选中一段谱子，用自然语言提出要求（"改简单点""转到 G 调""这几个小节换更丰富的和声"），云端分析后以**可预览、可撤销的编辑指令列表**形式回写乐谱。

- **用户**：音乐自学者/爱好者、音乐老师与学生。
- **默认形态**：插件本体开源，云端服务默认指向**用户自带的 LLM API Key**（支持 OpenAI 兼容接口），亦可自托管。

---

## 3. 用户画像与核心场景

| 场景 | 用户 | 诉求 | 对应功能 |
|---|---|---|---|
| S1 弹喜欢的曲子 | 自学者 | 原谱太难，想弹简化版 | 难度简化 |
| S2 适配自己嗓音/乐器 | 自学者/爱好者 | 原调不合适 | 转调 |
| S3 备课分层 | 老师 | 同一曲目给不同水平学生 | 难度简化（分档） |
| S4 和声教学演示 | 老师 | 展示同一旋律的不同和声可能性 | 局部和弦重配（多方案预览） |
| S5 练习难点攻破 | 学生 | 某几小节织体太复杂 | 局部简化/加花 |

**MVP 优先级**：S1/S2/S3（简化 + 转调）先行，S4/S5（局部重配/加花）二期。

## 4. 核心功能需求（v0.1）

### F1 转调（Transpose）

- 输入：选中片段（默认全曲）、目标（目标调名 **或** 目标音域范围）。
- 规则引擎完成，确定性输出；云端仅负责调性检测辅助。
- 输出：一条 `transpose` 编辑指令，可预览（绿色高亮预览模式）后应用或撤销。

### F2 难度简化（Simplify）

- 输入：选中片段、目标难度档位（简单 / 中等 / 原谱不变）。
- 规则为主、LLM 做决策：
  - 确定性规则：去装饰音、拆分过宽和弦、降低织体密度、压缩音域、简化节奏（见 §8）。
  - LLM 决策：**改哪里、改到什么程度**（哪些小节、触发哪些规则），输出结构化 JSON。
- 输出：一组编辑指令（按小节分区），用户可**逐条接受/拒绝**。

### F3 局部和弦重配 / 加花（Reharm / Embellish）——二期

- 输入：选中若干小节 + 风格倾向（如"更爵士""更丰富"）。
- LLM 输出目标和弦进行 + 加花建议 → 规则校验（调内和弦、声部进行、平行五八度）→ **建议模式**：给出 2-3 个方案供预览选择。
- 约束：只作用于选中小节，不重写其他部分。

### F4 编辑指令预览与回滚（贯穿所有功能）

- 云端回传的**不是整谱**，而是编辑指令列表；每条含：类型、作用范围、改动说明、理由。
- 插件逐条应用：支持高亮预览 → 接受 / 拒绝 → 撤销（走 MuseScore undo 栈）。
- 一次改编可"全接受""全拒绝""挑着接受"。

### F5 设置页

- LLM API Key（本地存储）、Base URL（默认 OpenAI，兼容 DeepSeek/通义/Ollama 等）、模型名、Token 上限。
- 隐私声明展示（见 §10）。
- 中英双语并行 UI（v0.1 起即用 i18n 文案表，默认跟随系统语言，可手动切换）。

---

## 5. 非目标（v1 明确不做）

- ❌ 整曲风格改写（流行→爵士全曲转换）
- ❌ 自动换编制/配器（钢琴→弦乐四重奏）
- ❌ 自动生成分谱
- ❌ 音频处理（输入输出都是乐谱，不是音频）
- ❌ 从零生成新曲
- ❌ 支持 MuseScore 3（仅支持 MS 4.x，降低兼容负担）

## 6. 架构设计

```
┌─────────────────────┐         ┌──────────────────────────────┐
│  MuseScore 4 插件(QML) │  HTTP   │        云端服务 (FastAPI)      │
│                      │ ◄──────► │  ┌────────────────────────┐  │
│  · 选区交互           │  JSON    │  │ 确定性层 (Python+music21)│  │
│  · 指令列表 UI/预览   │         │  │  调性/音域/难度/规则     │  │
│  · 逐条应用+撤销      │         │  └───────────┬────────────┘  │
│  · 设置页             │         │  ┌───────────▼────────────┐  │
└─────────────────────┘         │  │ 创意层 (LLM, 用户Key)    │  │
                                │  │  结构化决策 JSON         │  │
                                │  └───────────┬────────────┘  │
                                │  ┌───────────▼────────────┐  │
                                │  │ 校验层 (规则检查+重试)    │  │
                                │  └───────────┬────────────┘  │
                                │              ▼              │
                                │       编辑指令集 JSON         │
                                └──────────────────────────────┘
```

**关键决策：回传"编辑指令集"而非整谱。** 好处：可预览、可逐条接受、可撤销、token 消耗小、用户对结果有掌控感。

### 6.1 插件端（QML）

- 从选区导出结构化摘要（MusicXML 或轻量 JSON，含音符/和弦/装饰音/调性线索）。
- `XMLHttpRequest` POST 到用户配置的云端地址。
- 渲染指令列表：类型图标、范围小节、说明、理由、接受/拒绝按钮。
- 应用指令走 MuseScore API（`cursor`/`note`/`chord` 操作），包在 undo 事务里。

### 6.2 云端服务（Python 3.11 + FastAPI + music21）

- `POST /api/arrange`：输入摘要 + 用户指令 + 目标参数 → 输出指令集。
- `POST /api/analyze`：调性检测（Krumhansl-Schmuckler 等）、音域、难度评分。
- `GET /health`、`GET /api/config`（服务端支持的模型/能力声明）。
- 无状态、无数据库；请求结束即释放。

## 7. 数据与接口设计（草案）

> **摘要协议决策：自定义 JSON**（轻量、token 少、QML 端解析简单、schema 完全可控）。MusicXML 仅保留为调试/与外部工具互通的可选导出格式，**不作为主协议**。

### 7.1 ScoreSummary（摘要，发给 LLM 的输入）

```jsonc
{
  "title": "…", "time_signature": "4/4", "key_estimate": "G major",
  "measures": 32, "voices": 2,
  "range": { "low": "C3", "high": "C6" },
  "difficulty_features": { "note_density": 0.42, "max_chord_span": 14, "ornament_count": 12, "rhythm_complexity": 0.3 },
  "selected": { "start_measure": 8, "end_measure": 16 },
  "excerpt": "…旋律片段简化表示（前 N 小节，控制 token）…"
}
```

### 7.2 EditInstruction（编辑指令，云端输出）

```jsonc
{
  "id": "e1",
  "type": "transpose | simplify | reharmonize | embellish | …",
  "scope": { "start_measure": 8, "end_measure": 16, "voices": [0, 1] },
  "params": { "semitones": 3, "rules": ["drop_ornaments", "split_chords"], "target_range": "…" },
  "description": "第 8-16 小节：删除装饰音并拆分左手过宽和弦",
  "rationale": "密集装饰音超出初级难度，拆分后织体更薄"
}
```

### 7.3 主要 API

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/arrange` | POST | 改编主入口，返回指令集 + 校验报告 |
| `/api/analyze` | POST | 返回调性/音域/难度评分 |
| `/api/health` | GET | 存活检查 |
| `/api/config` | GET | 能力声明（供插件展示可用功能） |

## 8. 规则引擎 v0.1 规则集

### 难度评分（0-1）

`难度 = w1·密度 + w2·音域跨度 + w3·和弦宽度 + w4·装饰音密度 + w5·节奏复杂度`（权重先凭经验，基准集上标定）。

### 简化规则（确定性，可组合）

| 规则 | 说明 | 默认档位 |
|---|---|---|
| `drop_ornaments` | 删除倚音/波音/颤音/回音 | 简单 |
| `split_chords` | 跨度 > 10 度的和弦拆分或转位 | 简单 |
| `reduce_density` | 重复八度去重、重复音型减半 | 简单 |
| `compress_range` | 音域压缩到目标范围（默认钢琴 C2–C6） | 简单 |
| `simplify_rhythm` | 32 分→16 分、三连音→八分（可配置是否保留） | 简单 |
| `keep_melody` | 旋律声部（最高声部）永不删除，只做简化 | 硬约束 |

### 校验规则（任何改编输出必须通过）

- 音域不超界（钢琴 21–108；可被用户目标覆盖）。
- 声部不交叉、不重叠（重配时）。
- 和弦音在目标调内，或带和弦标记明确离调意图。
- 无平行五八度（仅重配/加花时检查）。
- 旋律声部保留原节奏骨架比例（简化后节拍数不变，保持小节对齐）。

## 9. LLM 层设计

### 输入

- ScoreSummary（**不是整谱**，控制 token）+ 用户自然语言指令 + 目标用户水平（初级/中级）+ 可用规则清单。

### 输出（JSON Schema 强约束）

- 决策列表：`[{action, scope, params, rationale}]`，action 必须来自枚举。
- 系统提示词里给出完整 schema 与示例；解析失败自动重试 1 次。

### 降级策略（质量兜底）

1. LLM 决策经校验层失败 → 自动重试 1 次（修正提示）。
2. 仍失败 → 丢弃该条决策，回退为**纯规则保守方案**（如"整段只做 drop_ornaments"）。
3. 规则也失败 → 返回明确错误信息给用户（不静默失败）。

### 成本控制

- 只发摘要不发整谱；摘要长度上限（如旋律 40 小节/400 token）。
- 用户可设 Token 上限；超限时只处理选区部分。
- 默认模型建议：DeepSeek/GPT-4o-mini 级别即可（任务以结构化决策为主，不要求音乐生成能力）。

## 10. 版权与隐私（合规基线）

- **本地优先 + 不存储 + 用户自担责任**。
- 谱面数据仅存在于请求处理内存中，请求结束即释放；服务端无数据库。
- 日志脱敏：只记功能调用、耗时、token 数，**不记谱面内容**。
- 插件设置页明示："上传乐谱即代表你有权处理该谱子；数据不会存储或用于训练。"
- 不做任何用户谱子的入库/训练；不使用用户谱子改进提示词模板。

## 12. 验收标准与基准集

### 基准集（现在就建，20 首）

- 构成：古典入门（小步舞曲、简易奏鸣曲）8 首 + 流行/影视改编谱 6 首 + 练习曲（车尔尼等）4 首 + 用户自定义 2 首。
- 每首标注：原始难度、可演奏性、音乐性基线。

### 验收打分（每次改动跑全量）

| 维度 | 说明 | 分值 |
|---|---|---|
| 可演奏性 | 目标水平人群能否顺畅演奏 | 0-5 |
| 音乐性 | 简化后是否仍"好听、像原曲" | 0-5 |
| 忠实度 | 与原谱差异是否可解释、可控 | 0-5 |

- 门禁：任何改动不得让基准集总分下降（防"越改越差"）。

### 功能验收清单（v0.1 发布门槛）

- [ ] F1 转调：全曲/选区、目标调/目标音域两种输入，误差为 0
- [ ] F2 简化：三个难度档位在基准集上可演奏性平均 ≥ 4
- [ ] F4 指令预览/接受/拒绝/撤销全链路无崩溃
- [ ] F5 设置页：Key 校验、Base URL 可切换（实测 OpenAI 与 DeepSeek 兼容端点）
- [ ] 隐私：日志抽样检查无谱面内容

## 14. 风险与开放问题

| 风险 | 影响 | 对策 |
|---|---|---|
| QML 插件 API 版本差异（MS 4.0-4.5） | 兼容性 | 锁定 MS 4.x 最低版本，CI 里跑 4.4/4.5 冒烟 |
| 回写操作的原子性与撤销 | 用户体验 | 每条指令独立事务 + 应用前全量备份选区 |
| LLM 输出质量不稳定 | 口碑 | 校验层 + 降级策略 + 建议模式（二期） |
| XMLHttpRequest 在插件沙箱中的可用性 | 架构可行性 | **已实测可行**（4.7 form 扩展同步 XHR 200 OK） |
| 基准集人工打分耗时 | 迭代效率 | 打分表半结构化，先人工后考虑辅助评分 |
| ~~4.7 无删除音符 API~~ **✅ 已解决**：`note.parent.remove(note)`（开源插件 fretboard-plugin 证实的写法） | 曾阻塞去重复八度写回 | 实测删除成功；后续拆和弦/删装饰音沿用同一方法 |

### 开放问题（已定案）

1. 开发者是 QML 新手 → 插件开发借助辅助工具完成；用户只需会安装/运行插件并反馈错误。
2. 摘要协议 → **自定义 JSON**（理由见 §7 决策）。
3. UI 语言 → **中英双语并行**（i18n 文案表，v0.1 起生效）。
4. 工作名 → **谱伴 / ScoreMate**（已定案）。

### 实测记录（里程碑 0-2 验证结论）

- ✅ MuseScore 4.7.4：老插件系统可加载但**创建窗口被禁**、异步回调不执行 → 已整体迁移到**新扩展系统**（manifest.json + form QML）
- ✅ 新扩展系统：同步 XMLHttpRequest → 云端 **200 OK**（网络可行）
- ✅ 写回机制：`note.pitch` 可读写 + `startCmd/endCmd` 撤销事务 → 移调实测成功（动、显示对、Ctrl+Z 可撤销）
- ✅ 和弦识别：`note.parent.notes` 有效；重复八度检测 6/6 精准
- ❌ ~~音符删除不可用~~ → **✅ `note.parent.remove(note)` 实测成功**（开源插件 fretboard-plugin 参考）；去重复八度写回可用
- ✅ 简化写回实测：**压缩音域**（八度平移）、**去重复八度**（chord.remove）均成功 → MVP 写回三件套：转调 / 压缩音域 / 去重复八度
- ✅ 测试谱 6 份 + 端到端验证脚本 6/6 通过（见 test-scores/）
